# 三、第一优先级：Core 里面的 Message 设计不够“六边形”

这是我认为架构层面**最值得改的一个问题**。

现在：

```text
core
└── port
    └── output
        └── messaging
            ├── Message
            ├── MessagePublisher
            └── TrafficMessageTypes
```

其中 `Message`：

```java
public class Message<T> {

    private String messageId;
    private String messageType;
    private String topic;
    private String tag;
    private String key;
    private T payload;
    private Map<String, String> headers;
    private Instant timestamp;
    private String schemaVersion;
    private String source;
    private String traceId;
    private String correlationId;
}
```

这里已经开始出现**基础设施概念泄漏到 Core**。

例如：

```text
topic
tag
headers
messageType
schemaVersion
```

特别是：

```java
private String tag;
```

这个其实明显是 RocketMQ 思维。

Core 不应该知道：

> “我要往 RocketMQ Topic + Tag 发消息。”

Core 应该只知道：

> “我要发布一个交通指标事件。”

# 五、第二个非常严重的问题：SUMO 异步执行现在实际上有功能漏洞

这是我检查代码后认为最需要马上处理的问题之一。

现在：

```java
SimulationEnginePort
```

里有：

```java
default String runAsync(SumoSimulationRequest request) {
    Thread t = new Thread(() -> run(request));
    t.setDaemon(true);
    t.start();
    return request.simulationId();
}
```

这里有两个问题。

## 1. Core Port 不应该自己创建 Thread

这是非常典型的架构边界错误。

Core：

```java
new Thread(...)
```

实际上开始承担：

> 并发模型 / 线程管理 / 异步执行策略

这是 Infrastructure / Application Runtime 的职责。

应该由 Adapter 或专门的 Job/Executor 管理。

---

# 六、更严重的是：SUMO async 模式下结果可能直接丢失

现在 `SumoTrafficSimulator`：

```java
if (properties.isAsyncRun()) {

    String started = sumoSimulationPort.runAsync(...);

    logger.info("Started async SUMO simulation...");
    return;
}
```

也就是说：

```text
runAsync()
   ↓
立即 return
   ↓
SumoTrafficSimulator return
```

而 `SimulationEnginePort` 的默认实现：

```java
new Thread(() -> run(request))
```

只是：

```text
后台执行 run()
```

但是：

```java
run()
 ↓
List<SumoTripInfo>
 ↓
没有人接收
 ↓
没有 Mapper
 ↓
没有 publish
```

也就是说：

> **异步模式下 SUMO 跑完以后，结果很可能没人处理。**

而配置里的：

```yaml
asyncRun: true
```

还是默认值。

这属于 **P0/P1 级别功能问题**。

# 七、这个地方应该怎么改

不要：

```java
SimulationEnginePort.runAsync()
```

更不要在 Port 里：

```java
new Thread(...)
```

建议变成：

```java
SimulationJobPort
```

例如：

```java
public interface SimulationJobPort {

    String submit(SimulationRequest request);

    void cancel(String simulationId);

    SimulationStatus status(String simulationId);

}
```

然后：

```text
Application
     │
     │ submit
     ↓
SimulationJobPort
     │
     ↓
DockerSimulationJobAdapter
     │
     ├── Executor
     ├── Process
     ├── SUMO
     │
     ↓
SimulationCompleted Event
     │
     ↓
Application Handler
     │
     ↓
MetricStore / EventPublisher
```

或者简单一点：

```java
public interface SimulationEnginePort {

    SimulationResult run(SimulationRequest request);
}
```

异步调度完全放在 Adapter：

```java
@Component
class DockerSimulationJobAdapter {

    private final ExecutorService executor;

    public String submit(...) {
        executor.submit(() -> {
            SimulationResult result = engine.run(...);
            eventPublisher.publish(...);
        });
    }
}
```

**Core 不负责线程。**

这个问题比一般代码问题严重，因为它会直接污染数据库里的业务数据。

```java
    double travelTimeMinutes = (ROAD_LENGTH / averageSpeed) * 60;
    return travelTimeMinutes;
}
```

这里返回的是：

> 分钟

但是：

```java
SumoTrafficMetricMapper
```

里面：

```java
double averageDuration =
    trips.stream()
         .mapToDouble(SumoTripInfo::durationSeconds)
         .average()
         .orElse(0);
```

这里返回的是：

> 秒

最终都放进：

```java

```

也就是说：

```text
SimulationTrafficGenerator
averageTravelTime = minute

SUMO
averageTravelTime = second
```

数据库字段却是同一个：

```text
averageTravelTime
```

这是非常严重的领域模型问题。

# 二十一、Victoria Adapter 的 Retry 设计也需要调整

目前 retry 使用：

```java
Thread.sleep(delay);
```

虽然在专用 scheduler 中运行，不会阻塞业务线程，但依然会：

```text
scheduler
   ↓
Thread.sleep()
   ↓
整个 flush worker 被占用
```

更好的做法是：

```java
scheduler.schedule(
    retryTask,
    delay,
    TimeUnit.MILLISECONDS
);
```

你其实在 `VictoriaMetricAdapter` 后半段已经部分采用这种思路了。

应该统一，不要一部分：

```text
sleep
```

一部分：

```text
schedule
```

## 最重要的 10 个整改点

如果你准备把这个项目作为一个正式的技术项目/架构项目继续往下做，我建议先锁死下面 10 条：

1. **Core 不允许出现 RocketMQ/Spring Event 等技术消息模型。**
2. **Core Port 不允许自己创建 Thread / Executor。**
3. **SUMO async 必须保证“任务提交 → 执行 → 结果 → 入库/事件”完整闭环。**
4. **所有交通指标必须明确单位。**
5. **Domain Model 必须有基本业务不变量。**
6. **Message Converter 必须一对一明确路由，不能依赖 List 顺序。**
7. **所有缓存/队列必须有容量上限。**
8. **MQ reliability 必须从 InMemory 升级到 Inbox/Outbox 或等价机制。**
9. **配置统一归 Bootstrap，生产密钥全部外置。**
10. **ArchUnit + Unit + Integration + Contract 四类测试一起建立起来。**

如果按照这个方向整改，最终可以真正形成：

```text
                 ┌──────────────────────┐
                 │      Bootstrap        │
                 │   Composition Root    │
                 └──────────┬───────────┘
                            │
       ┌────────────────────┼────────────────────┐
       ↓                    ↓                    ↓
```
