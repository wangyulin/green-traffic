可以。我们这一次先**不要急着改所有代码**，先把 `InfluxTestController → Application → Port → Influx/VM` 这条链路设计正确。后面每一轮再落一个具体改造点。

结合你当前源码，核心问题其实非常明确：

```text
InfluxTestController
        │
        ▼
TrafficRepository        ← 这是旧的“业务仓储接口”
        │
   ┌────┴────┐
   ▼         ▼
Influx      VictoriaMetrics
```

而项目里同时又存在：

```text
MetricService
    │
    ▼
MetricWritePort
```

所以现在实际上是**两套架构并存**。

# 一、我们最终要达到什么效果？

我建议 GreenTraffic 最终采用下面这种标准六边形结构：

```text
                         外部世界
                            │
             ┌──────────────┼──────────────┐
             │              │              │
          REST API       MQ Consumer     Scheduler
             │              │              │
             ▼              ▼              ▼
       ┌────────────────────────────────────────┐
       │              INPUT ADAPTER              │
       │                                        │
       │ InfluxTestController                   │
       │ TrafficMessageConsumer                 │
       │ TrafficDataScheduler                  │
       └───────────────────┬────────────────────┘
                           │
                           ▼
       ┌────────────────────────────────────────┐
       │               INPUT PORT                │
       │                                        │
       │ WriteTrafficMetricUseCase              │
       │ QueryTrafficMetricUseCase              │
       └───────────────────┬────────────────────┘
                           │
                           ▼
       ┌────────────────────────────────────────┐
       │             APPLICATION CORE           │
       │                                        │
       │ TrafficMetricApplicationService        │
       │ TrafficDataQueryService                │
       │ Domain Service                         │
       └───────────────────┬────────────────────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
       ┌────────────┐ ┌───────────┐ ┌────────────┐
       │ Output     │ │ Output    │ │ Output     │
       │ Port       │ │ Port      │ │ Port       │
       │ Write      │ │ Query     │ │ Publish    │
       └─────┬──────┘ └─────┬─────┘ └─────┬──────┘
             │              │             │
             ▼              ▼             ▼
         InfluxDB       Influx/VM      RocketMQ
         Adapter        Adapter        Adapter
```

这里最重要的一条原则：

> **Core 只定义“我要做什么”，Infrastructure 才负责“具体怎么做”。**

# 二、先解决 `InfluxTestController`

你现在的 Controller 是：

```java
@RestController
@RequestMapping("test/influx")
public class InfluxTestController {

    private final TrafficRepository repository;

    public InfluxTestController(TrafficRepository repository) {
        this.repository = repository;
    }

    @PostMapping("/write")
    public String write() {
        TrafficMetric metric = ...
        repository.save(metric);
        return "OK";
    }

    @GetMapping("/read")
    public List<TrafficMetric> read() {
        ...
        return repository.query(start, stop);
    }
}
```

这里有三个问题。

### 问题 1：Controller 直接依赖 Repository

```text
Controller
   ↓
Repository
```

这是不标准的。

Controller 不应该关心：

> “数据保存到哪里？”

它只应该关心：

> “用户请求我要执行哪个业务用例？”

---

### 问题 2：Controller 创建业务对象

现在：

```java
new TrafficMetric(...)
```

也是业务逻辑的一部分。

Controller 最好只负责：

```text
HTTP Request
     ↓
Request DTO
     ↓
Input Port
```

---

### 问题 3：Controller 知道“Influx”

更严重的是：

```java
@RequestMapping("test/influx")
```

这个 Controller 从名字上就和 InfluxDB 绑定了。

如果以后生产环境：

```text
dev     → InfluxDB
test    → InfluxDB
prod    → VictoriaMetrics
```

Controller 不应该发生任何变化。

---

# 三、第一步：建立 Input Port

我们先创建：

```text
green-traffic-core
└── src/main/java
    └── com.greentraffic.core
        └── port
            └── input
                ├── WriteTrafficMetricUseCase.java
                └── QueryTrafficMetricUseCase.java
```

## 1. 写入 Input Port

```java
package com.greentraffic.core.port.input;

import com.greentraffic.core.domain.traffic.TrafficMetric;

public interface WriteTrafficMetricUseCase {

    void write(TrafficMetric metric);
}
```

它表达的是：

> 系统支持“写入交通指标”这个业务用例。

注意：

它**不知道 InfluxDB**。

也不知道：

```text
MySQL
VictoriaMetrics
TDengine
Kafka
RocketMQ
```

# 四、建立查询 Input Port

```java
package com.greentraffic.core.port.input;

import com.greentraffic.core.domain.traffic.TrafficMetric;

import java.time.Instant;
import java.util.List;

public interface QueryTrafficMetricUseCase {

    List<TrafficMetric> query(
            Instant start,
            Instant end
    );
}
```

现在 Core 对外暴露两个业务能力：

```text
WriteTrafficMetricUseCase
QueryTrafficMetricUseCase
```

这就是六边形架构的：

> **Input Ports**

# 五、Application Service 实现 Input Port

然后修改你现在的：

```text
MetricService
```

让它成为：

```java
@Service
public class MetricApplicationService
        implements WriteTrafficMetricUseCase {

    private final MetricWritePort writePort;

    public MetricApplicationService(
            MetricWritePort writePort) {
        this.writePort = writePort;
    }

    @Override
    public void write(TrafficMetric metric) {

        MetricPoint point = new MetricPoint(
                metric.roadId(),
                metric.direction(),
                metric.vehicleType(),
                metric.trafficFlow(),
                metric.averageSpeed(),
                metric.co2Emission(),
                metric.location(),
                metric.timestamp()
        );

        writePort.write(List.of(point));
    }
}
```

这时候关系变成：

```text
                INPUT
                  │
                  ▼
       WriteTrafficMetricUseCase
                  ▲
                  │
                  │ implements
                  │
       MetricApplicationService
                  │
                  ▼
          MetricWritePort
                  │
                  ▼
             Adapter
```

这才是标准六边形的基本形态。

# 六、然后 Controller 只依赖 Input Port

现在：

```java
@RestController
@RequestMapping("/traffic")
public class InfluxTestController {

    private final WriteTrafficMetricUseCase writeUseCase;
    private final QueryTrafficMetricUseCase queryUseCase;

    public InfluxTestController(
            WriteTrafficMetricUseCase writeUseCase,
            QueryTrafficMetricUseCase queryUseCase) {

        this.writeUseCase = writeUseCase;
        this.queryUseCase = queryUseCase;
    }
}
```

注意这里发生了一个非常重要的变化：

原来：

```text
InfluxTestController
       ↓
TrafficRepository
```

现在：

```text
InfluxTestController
       ↓
WriteTrafficMetricUseCase
       ↓
MetricApplicationService
```

Controller 已经不知道 InfluxDB 了。

# 七、那么 InfluxDB 到底在哪里？

在 Infrastructure：

```text
green-traffic-infrastructure
└── persistence
    └── influxdb
        ├── config
        ├── client
        ├── mapper
        └── adapter
            └── InfluxTrafficMetricAdapter.java
```

它实现：

```java
public class InfluxTrafficMetricAdapter
        implements MetricWritePort {
```

所以：

```text
Core

MetricWritePort
      ▲
      │ implements
      │
InfluxTrafficMetricAdapter
```

这是：

> **Output Adapter**

# 八、真正漂亮的地方来了：VM 怎么办？

假设：

```text
开发环境：
InfluxDB

测试环境：
InfluxDB

生产环境：
VictoriaMetrics
```

Core 完全不用改。

```text
                    MetricWritePort
                           ▲
             ┌─────────────┴─────────────┐
             │                           │
             │                           │
    InfluxTrafficMetricAdapter    VictoriaMetricAdapter
             │                           │
             ▼                           ▼
          InfluxDB                 VictoriaMetrics
```

然后 Spring 根据配置决定到底装哪个 Adapter。

例如：

```yaml
traffic:
  storage:
    type: influx
```

开发环境：

```yaml
traffic:
  storage:
    type: influx
```

生产环境：

```yaml
traffic:
  storage:
    type: victoria-metrics
```

**Controller 不变。**

**Application Service 不变。**

**Input Port 不变。**

**Output Port 不变。**

只有：

```text
Infrastructure Adapter
```

发生切换。

这就是我们真正想要的：

> **同一个业务核心，不同基础设施实现。**

# 九、但是这里有一个关键问题

你当前项目使用：

```java
@ConditionalOnProperty
```

例如：

```java
@ConditionalOnProperty(
    name = "metrics.sink",
    havingValue = "vm"
)
```

这种方式**可以用**，但我不建议我们最终让整个架构大量依赖这种写法。

更好的设计是：

```text
application.yml
        │
        ▼
StorageProperties
        │
        ▼
Infrastructure Configuration
        │
   ┌────┴─────┐
   ▼          ▼
Influx       VM
Adapter     Adapter
```

下一步我们就专门解决：

> **“如何让 Spring 根据 `traffic.storage.type` 自动选择 InfluxDB / VictoriaMetrics Adapter，而且 Core 完全不知道 Spring 的 `@ConditionalOnProperty`。”**

# 十、这一轮先不要动旧代码

非常重要。

现在不要直接删除：

```text
TrafficRepository
TrafficDataRepository
MetricService
InfluxTrafficRepository
VictoriaTrafficRepository
```

因为目前项目里存在**两套链路**：

```text
旧链路：

Controller
   ↓
TrafficRepository
   ↓
Influx / VM
```

以及：

```text
新链路：

MetricService
   ↓
MetricWritePort
   ↓
Influx / VM
```

我们应该采用：

> **渐进式迁移，而不是一次性推倒重写。**

下一轮建议只做一件事情：

### 把 `InfluxTestController` 正式改造成：

```text
InfluxTestController
        ↓
WriteTrafficMetricUseCase
        ↓
MetricApplicationService
        ↓
MetricWritePort
        ↓
InfluxTrafficMetricAdapter
```
