# 一、先给结论：当前架构成熟度

如果以标准 Hexagonal Architecture / Ports & Adapters 为基准，我会给目前代码：

> **架构成熟度：约 55～60 分 / 100**
>
> **属于“已经搭出了六边形的形状，但核心边界还没有真正封闭”。**

比较明显的问题不是“有没有 Port/Adapter 目录”，而是：

**模块虽然拆开了，但依赖方向、模型边界、事务边界、事件边界、持久化边界还没有完全建立起来。**

标准六边形的核心要求实际上是：

> Domain/Application Core 不应该知道 HTTP、JPA、MySQL、WebSocket、Spring Event 等技术细节；外部世界通过 Port 进入/离开 Core，Adapter 负责实现 Port。

这也是 Ports & Adapters 的核心思想，而不是简单的目录划分。([DeepWiki][2])

# 三、P0：最核心的问题——“模块拆了，但依赖倒置还不彻底”

这是我认为这个项目现在**第一优先级**的问题。

目前仓库的模块关系本身已经比较接近：

```text
common
   ↓
model
   ↓
core
   ↓
api / push / simulator
```

同时 infrastructure 作为独立模块存在。

但从六边形架构的标准来看，真正应该追求的是：

```text
             ┌─────────────────────┐
             │   Driving Adapters  │
             │                     │
             │ REST / WebSocket    │
             │ Simulator / MQ      │
             └──────────┬──────────┘
                        ↓
                ┌───────────────┐
                │ Input Ports   │
                ├───────────────┤
                │ Application   │
                │ Services      │
                ├───────────────┤
                │ Domain        │
                │ Model         │
                ├───────────────┤
                │ Output Ports  │
                └───────┬───────┘
                        ↓
             ┌─────────────────────┐
             │ Driven Adapters     │
             │                     │
             │ JPA / MySQL         │
             │ WebSocket           │
             │ MQ / Redis          │
             └─────────────────────┘
```

也就是说：

> **Core 只认识 Port，不认识 Adapter。**

这是整改的第一原则。

# 四、P0-1：Repository 必须彻底做“端口化”

这是我建议你重点整改的一块。

当前项目已经把 `Repository` 概念放进 Core，这是方向正确的。

但是要进一步确认：

### Core 中应该只有

```java
public interface TrafficDataRepository {

    TrafficData save(TrafficData data);

    Optional<TrafficData> findById(TrafficDataId id);

    List<TrafficData> findLatest(...);

}
```

而不能让 Core 出现：

```java
JpaRepository
EntityManager
Specification
Pageable
@Query
@Entity
Hibernate
```

这些都应该属于 Infrastructure。

最终：

```text
core
 └── port
      └── output
           └── TrafficDataRepository

infrastructure
 └── adapter
      └── persistence
           ├── JpaTrafficDataRepository
           ├── TrafficDataEntity
           └── TrafficDataRepositoryAdapter
```

形成：

```text
Core
  ↓
TrafficDataRepository
  ↑
JpaTrafficDataRepositoryAdapter
  ↓
JPA
```

这才是标准六边形。

# 五、P0-2：必须把三种 Model 分开

这是这个项目下一阶段非常重要的一项。

现在最容易出现的架构污染就是：

```text
DTO
Entity
Domain Object
```

互相混用。

尤其是交通数据这种系统。

我建议明确建立：

### 1. API DTO

例如：

```java
TrafficDataRequest
TrafficDataResponse
TrafficAnalysisResponse
```

只负责 HTTP。

---

### 2. Domain Model

例如：

```java
TrafficData
Intersection
CarbonEmission
OptimizationAdvice
```

这些对象应该表达业务。

比如：

```java
TrafficData.calculateEmission()
```

或者：

```java
CarbonEmissionCalculator.calculate(TrafficData data)
```

而不是：

```java
TrafficDataDTO
```

贯穿整个业务链。

---

### 3. Persistence Entity

例如：

```java
TrafficDataEntity
IntersectionEntity
OptimizationAdviceEntity
```

只能服务于数据库。

---

最终形成：

```text
HTTP
 ↓
Request DTO
 ↓
Input Port
 ↓
Application Service
 ↓
Domain Model
 ↓
Output Port
 ↓
Persistence Adapter
 ↓
Entity
 ↓
Database
```

而不是：

```text
Controller
 ↓
DTO
 ↓
Service
 ↓
DTO
 ↓
Repository
 ↓
Entity
```

后者虽然能跑，但是六边形的价值基本被削弱了。

# 六、P0-3：Application Service 和 Domain Service 要重新划分

这是第二个架构重点。

现在 Core 里面有：

* 碳排放计算
* 优化规则
* 数据保存
* Event 发布

这些职责放在一个 Core 流程里是合理的，但需要进一步区分：

### Application Service

负责：

> **编排业务流程**

例如：

```java
ProcessTrafficDataUseCase
```

内部：

```text
1. 接收 TrafficData
2. 调用 CarbonEmissionCalculator
3. 调用 OptimizationEngine
4. 保存 TrafficData
5. 保存 Advice
6. 发布 TrafficDataProcessedEvent
```

---

### Domain Service

负责：

> **真正的业务规则**

例如：

```java
CarbonEmissionCalculator
TrafficOptimizationEngine
CongestionRule
EmissionRule
```

它们不应该关心：

```text
Spring
JPA
MySQL
WebSocket
ApplicationEventPublisher
```

---

所以应该形成：

```text
ProcessTrafficDataUseCase
          │
          ├── CarbonEmissionCalculator
          │
          ├── TrafficOptimizationEngine
          │
          ├── TrafficDataRepository
          │
          └── EventPublisher
```

这是非常典型的 Application Core。

# 七、P0-4：Spring Event 目前不能简单等同于“六边形事件”

这一点我建议特别注意。

项目现在大量使用：

```java
ApplicationEventPublisher
@EventListener
@Async
```

这本身不是问题。

问题在于：

> **Spring Event 是技术实现，不应该成为 Core 的业务抽象。**

如果 Core 里面直接：

```java
applicationEventPublisher.publishEvent(...)
```

那么 Core 就依赖 Spring。

这会破坏：

```text
Domain/Application
        ↓
Framework
```

正确方式应该是：

```java
public interface DomainEventPublisher {

    void publish(DomainEvent event);

}
```

Core：

```java
eventPublisher.publish(
    new TrafficDataProcessedEvent(...)
);
```

Infrastructure：

```java
@Component
class SpringEventPublisherAdapter
        implements DomainEventPublisher {

    private final ApplicationEventPublisher publisher;

    ...
}
```

这样：

```text
Core
 ↓
DomainEventPublisher
 ↑
SpringEventPublisherAdapter
 ↓
Spring
```

才是标准 Port & Adapter。

# 八、P1：Simulator 应该明确成为 Driving Adapter

这一点其实很容易改，而且收益很大。

现在 Simulator 是：

```text
@Scheduled
随机生成
TrafficDataDTO
发布 Event
```

架构上它实际上就是一个：

> **Driving Adapter / Input Adapter**

它不是 Core。

应该变成：

```text
Simulator Adapter
       ↓
GenerateTrafficDataUseCase
       ↓
Core
```

例如：

```java
public interface SubmitTrafficDataUseCase {

    void submit(TrafficDataCommand command);

}
```

Simulator：

```java
scheduler
   ↓
TrafficDataGenerator
   ↓
SubmitTrafficDataUseCase
```

这样以后：

```text
真实传感器
MQ
HTTP
文件
Simulator
```

都可以进入同一个 Use Case。

这是非常重要的扩展点。

### ❌ 误区二：有 `port` 包 = 六边形

也不是。

真正重要的是：

```text
谁定义 Port？
谁实现 Port？
谁依赖谁？
```

---

### ❌ 误区三：Spring Event = 解耦

不完全是。

它解决的是：

> **组件通信方式**

不自动解决：

> **架构依赖方向**

---

### ❌ 误区四：Repository 放 Core 就一定正确

只有：

```text
Core 定义接口
Infrastructure 实现接口
```

才成立。

---

### ❌ 误区五：现在就拆微服务

**不建议。**

这个项目当前最值得做的是：

> **先把 Modular Monolith + Hexagonal Architecture 做扎实。**

之后如果某个边界真的需要拆：

```text
Simulator
Push
Analysis
Traffic Processing
```

再拆微服务。

# 二十五、最后给你一个“整改优先级雷达”

我会把整个项目分成：

```text
                 P0
          ┌──────────────┐
          │ 依赖倒置     │
          │ Model隔离    │
          │ Repository   │
          │ Application  │
          └──────┬───────┘
                 │
       P1 ───────┼─────── P1
       Adapter   │       Event
       API       │       Transaction
       Simulator │       Common
       Push      │
                 │
          ┌──────┴───────┐
          │     P2       │
          │ CQRS-lite    │
          │ ArchUnit     │
          │ Test         │
          │ Observability│
          └──────────────┘
                 │
                 ▼
                P3
        Kafka / Redis / Flink
        微服务 / 容器化 / AI
```

**真正的主线只有一句话：**

> **先把 Core 变成一个不依赖 Spring/JPA/WebSocket/MySQL 的纯业务内核，再谈 Kafka、Redis、微服务。**

从当前代码状态看，这比继续增加功能、继续增加技术栈的收益大得多。项目当前的数据处理链路本身已经包含 Simulator → Core → 持久化 → ProcessedEvent → Push → Dashboard，这个链路非常适合作为一次完整的六边形架构重构样板。([GitHub][1])

另外，我注意到项目配置里仍存在开发环境数据库账号密码直接配置、H2 Console 暴露等工程化问题；这些虽然不是六边形架构问题，但如果目标是把项目提升到“可交付/可生产”的工程标准，应当列入后续 P1 安全整改。([GitHub][1])

**下一步我建议直接进入“代码级整改清单”**：逐个模块、逐个 package、逐个关键类列出 **“现状 → 违反哪条六边形原则 → 应移动到哪里 → 应新建什么 Port → 谁实现 → 最终依赖关系”**，并给每项标上 **P0/P1/P2 + 改造工作量 + 是否涉及接口变更**。这样就可以直接拿去作为这个项目的重构任务单。
