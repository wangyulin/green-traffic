你现在这个问题，本质上已经不是简单的“模块拆分”问题，而是需要把 **业务能力与基础设施实现解耦**。

你当前：

```text
green-traffic-core
green-traffic-push
green-traffic-simulator
...
```

如果 `core` 或 `push` 里面直接依赖 InfluxDB、RocketMQ，后面再增加 TDengine、IoTDB、Kafka、私有 MQ，就会逐渐变成：

```text
业务代码
   ↓
InfluxDB / RocketMQ
   ↓
公有云
```

最终很难支持：

```text
              ┌─ InfluxDB
              ├─ TDengine
业务能力 ─ SPI ┼─ IoTDB
              └─ ...
              
消息能力 ─ SPI ┬─ RocketMQ
              ├─ Kafka
              ├─ MQTT
              └─ 私有MQ
```

我建议你的 `green-traffic` 从现在的**业务模块化**进一步升级成：

> **领域/应用层 + 基础设施 SPI + 基础设施 Adapter + 平台装配层**

这会比较适合你这个“公有云 / 私有云 / 国产化基础设施适配”的场景。

# 二、最核心的变化：不要让 `core` 知道 InfluxDB / TDengine

这是整个设计最重要的一点。

例如现在可能存在：

```java
@Service
public class TrafficDataService {

    @Autowired
    private InfluxDBClient influxDBClient;

}
```

以后不要这么设计。

而应该：

```java
@Service
public class TrafficDataService {

    private final TimeSeriesRepository repository;

    public TrafficDataService(TimeSeriesRepository repository) {
        this.repository = repository;
    }
}
```

`TimeSeriesRepository` 是你的抽象：

```java
public interface TimeSeriesRepository {

    void save(TrafficMetric metric);

    List<TrafficMetric> query(QueryCondition condition);

}
```

然后：

```text
core
 │
 └── TimeSeriesRepository
          ↑
          │
    ┌─────┼───────────┐
    │     │           │
 Influx  TDengine   IoTDB
```

这就是典型的：

> **Hexagonal Architecture / Ports & Adapters**

或者从 Spring 项目的角度理解：

> **SPI / Adapter 架构**


# 五、`infrastructure-spi` 和 `core.port` 怎么选择？

这里实际上有两种方案。

## 方案 A：SPI 全部放 Core

例如：

```text
core
└── port
    └── outbound
        ├── TimeSeriesRepository
        └── MessagePublisher
```

这是我**更推荐**的。

因为这些接口本质上是业务应用需要的能力。

例如：

```text
TrafficAnalysisService
        ↓
TimeSeriesRepository
        ↓
TDengine
```

接口属于业务侧，而不是 TDengine。

这符合依赖倒置原则：

```text
Core
  ↑
  │ implements
  │
Adapter
```

---

## 方案 B：单独 `infrastructure-spi`

如果你的项目未来需要把基础设施能力作为一个**独立平台 SDK** 给多个业务系统使用，那么可以单独：

```text
green-traffic-infrastructure-spi
```

例如：

```java
public interface TimeSeriesClient {

    void write(...);

    List<?> query(...);

}
```

然后：

```text
green-traffic-infrastructure-influxdb
green-traffic-infrastructure-tdengine
green-traffic-infrastructure-iotdb
```

都实现它。

但是对于你现在的 Green Traffic，我更建议：

```text
core.port.outbound
```

作为业务侧 Port。

# 六、InfluxDB / TDengine / IoTDB 应该如何实现

例如：

```text
green-traffic-infrastructure-timeseries
│
├── green-traffic-infrastructure-influxdb
│   └── InfluxTimeSeriesRepository
│
├── green-traffic-infrastructure-tdengine
│   └── TdengineTimeSeriesRepository
│
└── green-traffic-infrastructure-iotdb
    └── IotdbTimeSeriesRepository
```

Influx：

```java
@Component
@ConditionalOnProperty(
    name = "green-traffic.timeseries.type",
    havingValue = "influxdb"
)
public class InfluxTimeSeriesRepository
        implements TimeSeriesRepository {

    @Override
    public void write(TrafficMetric metric) {
        // InfluxDB
    }
}
```

TDengine：

```java
@Component
@ConditionalOnProperty(
    name = "green-traffic.timeseries.type",
    havingValue = "tdengine"
)
public class TdengineTimeSeriesRepository
        implements TimeSeriesRepository {

    @Override
    public void write(TrafficMetric metric) {
        // TDengine
    }
}
```

IoTDB：

```java
@Component
@ConditionalOnProperty(
    name = "green-traffic.timeseries.type",
    havingValue = "iotdb"
)
public class IotdbTimeSeriesRepository
        implements TimeSeriesRepository {

    @Override
    public void write(TrafficMetric metric) {
        // IoTDB
    }
}
```

于是配置：

### 公有云

```yaml
green-traffic:
  timeseries:
    type: influxdb
```

### 私有云 A

```yaml
green-traffic:
  timeseries:
    type: tdengine
```

### 私有云 B

```yaml
green-traffic:
  timeseries:
    type: iotdb
```

业务代码完全不变。

```text
                                   ↓
                         ┌────────────────────┐
                         │ green-traffic-core │
                         └─────────┬──────────┘

                                   ↓
                 ┌────────────────────────────────┐
                 │       Infrastructure Adapter   │
                 │                                │
                 │ InfluxDB │ TDengine │ IoTDB    │
```

**绝对不要出现：**

```text

core → kafka
```

```text

│   └── green-traffic-platform-default
│
├── green-traffic-push
├── green-traffic-dashboard

```

**一句话概括这个重构方向：**

> `green-traffic-core` 不再关心“用什么技术”，只定义“我需要什么能力”；`infrastructure` 负责“这些能力怎么实现”；`platform` 负责“当前环境选择哪些实现”。

这样以后你增加 **TDengine、IoTDB、RocketMQ、Kafka、MQTT、国产数据库、国产 MQ**，本质上都只是新增 Adapter，而不是修改核心业务代码。

如果你的目标是把这个项目进一步做成**“一套代码、多云/私有云/国产化环境部署”**的架构，我下一步会重点把 **`green-traffic-core` 的 Port、SPI、Adapter、Spring Boot AutoConfiguration，以及 Maven dependencyManagement/BOM** 一起设计出来。这样会比单纯调整目录更重要，因为真正决定这个架构能否长期演进的是**依赖关系和自动装配机制**。
