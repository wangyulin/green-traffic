# 碳排放数据仿真模拟数据生成流程介绍

对于 **GreenTraffic**，InfluxDB 非常适合存储“交通传感器实时数据”这类**时序数据**。

我建议不要让 `simulator` 直接操作 InfluxDB，而是采用：

> **Simulator 负责生成数据 → Core 负责业务处理 → InfluxDB Repository 负责写入 → Push 负责实时推送**

这样后面把模拟数据源替换成真实传感器、Kafka、MQTT 时，核心业务基本不用改。

---

# 一、先理解为什么用 InfluxDB

你的系统会不断产生这样的数据：

```text
2026-08-20 20:50:01
传感器：SENSOR-001
道路：长安街-001
车辆数：125
平均速度：38.5 km/h
小汽车：80
公交车：10
卡车：15
新能源车：20
CO₂排放：32.6 kg
```

过 5 秒：

```text
2026-08-20 20:50:06
传感器：SENSOR-001
车辆数：132
平均速度：36.2 km/h
CO₂排放：35.1 kg
```

再过 5 秒：

```text
2026-08-20 20:50:11
...
```

这就是典型的：

> **时间 + 指标 + 标签**

所以非常适合 InfluxDB。

# 三、第一步：Simulator 生成交通数据

你的：

```text
green-traffic-simulator
└── TrafficSensorSimulator.java
```

负责模拟真实传感器。

例如每 5 秒执行一次：

```java
@Component
@RequiredArgsConstructor
public class TrafficSensorSimulator {

    private final TrafficDataGenerator trafficDataGenerator;
    private final TrafficDataService trafficDataService;

    @Scheduled(fixedDelay = 5000)
    public void generateTrafficData() {

        TrafficFlowDTO trafficFlow =
                trafficDataGenerator.generate();

        trafficDataService.process(trafficFlow);
    }
}
```

这里：

```text
TrafficDataGenerator
        ↓
生成 TrafficFlowDTO
        ↓
TrafficDataService
```

green-traffic-model

    ├── entity/
    ├── dto/

@Data
public class TrafficFlowDTO {

    private String sensorId;

     */

     * 小汽车数量
     */
    private Integer carCount;

     * 公交车数量

     */

# 五、第二步：进入 Core

然后：

```text
simulator
    ↓
TrafficDataService
```

这个 `TrafficDataService` 应该放在：

```text
green-traffic-core

core/
└── service/
    └── TrafficDataService.java
```

例如：

```java
@Service
@RequiredArgsConstructor
public class TrafficDataService {

    private final CarbonEmissionCalculator carbonEmissionCalculator;
    private final TrafficTimeSeriesRepository timeSeriesRepository;

    public void process(TrafficFlowDTO trafficFlow) {

        // 1. 计算碳排放
        CarbonEmission emission =
                carbonEmissionCalculator.calculate(trafficFlow);

        // 2. 保存时序数据
        timeSeriesRepository.save(
                trafficFlow,
                emission
        );

        // 3. 后续可以进行拥堵分析
        // 4. 后续可以产生领域事件
        // 5. 后续可以通知 push 模块
    }
}
```

这时候就出现了一个非常重要的设计：

```text
TrafficSensorSimulator
        ↓
TrafficDataService
        ↓
CarbonEmissionCalculator
        ↓
TrafficTimeSeriesRepository
        ↓
InfluxDB
```

# 六、为什么不让 Simulator 直接写 InfluxDB？

当然可以这样：

```text
Simulator
    ↓
InfluxDB
```

但是我**不推荐**。

因为 Simulator 的职责应该只是：

> “模拟传感器。”

如果写成：

```java
@Scheduled(...)
public void generate() {

    TrafficFlowDTO data = generator.generate();

    influxDBClient.write(data);
}
```

那么以后如果你把模拟器换掉：

```text
现在：

Simulator
 ↓
InfluxDB


以后：

Kafka
 ↓
InfluxDB
```

或者：

```text
MQTT
 ↓
InfluxDB
```

就会涉及大量代码修改。

更好的设计是：

```text
             ┌── simulator
             │
数据来源 ────┼── Kafka
             │
             ├── MQTT
             │
             └── HTTP
                    ↓
             TrafficDataService
                    ↓
              InfluxRepository
                    ↓
                 InfluxDB
```

这样数据来源和数据存储解耦。

# 七、第三步：Core 计算碳排放

这里就到了你的核心业务。

假设 Simulator 生成：

```text
车辆总数：100
小汽车：70
公交车：10
卡车：10
新能源车：10
平均速度：35 km/h
```

那么：

```text
TrafficFlowDTO
        ↓
CarbonEmissionCalculator
        ↓
计算 CO₂
        ↓
CarbonEmission
```

例如：

```java
@Component
public class CarbonEmissionCalculator {

    public CarbonEmission calculate(TrafficFlowDTO trafficFlow) {

        double carEmission =
                trafficFlow.getCarCount() * 0.12;

        double busEmission =
                trafficFlow.getBusCount() * 0.80;

        double truckEmission =
                trafficFlow.getTruckCount() * 1.20;

        double total =
                carEmission
                + busEmission
                + truckEmission;

        return CarbonEmission.builder()
                .totalEmission(total)
                .build();
    }
}
```

这里的公式只是示例，真正项目中应该根据你的排放因子、车辆类型、速度、燃料类型等建立计算模型。

# 八、第四步：写入 InfluxDB

这里建议在：

```text
green-traffic-core
└── repository/
```

增加一套**时序数据 Repository**。

例如：

```text
repository/
├── TrafficFlowRepository.java
├── CarbonEmissionRepository.java
└── influx/
    ├── InfluxTrafficRepository.java
    └── InfluxCarbonEmissionRepository.java
```

这里需要注意：

你现在项目里面的：

```text
repository/
```

如果使用：

```java

```

那么它是面向 MySQL/PostgreSQL 这种关系型数据库的。

**InfluxDB 不应该强行塞进 JPA Repository。**

建议明确区分：

```text
JPA Repository
        ↓
MySQL / PostgreSQL

TimeSeries Repository
        ↓
InfluxDB
```

# 九、InfluxDB 里面的数据怎么设计？

这是整个流程中非常关键的一部分。

InfluxDB 的核心概念可以简单理解成：

```text
Measurement
    ↓
Tags
    ↓
Fields
    ↓
Timestamp
```

对于你的系统，我建议设计：

```text
Measurement:
traffic_flow
```

Tags：

```text
sensor_id
road_id
direction
```

Fields：

```text
vehicle_count
average_speed
car_count
bus_count
truck_count
new_energy_count
carbon_emission
```

Timestamp：

```text
collect_time
```

也就是：

```text
traffic_flow
│
├── Tags
│   ├── sensor_id = SENSOR-001
│   ├── road_id   = ROAD-001
│   └── direction = NORTH
│
├── Fields
│   ├── vehicle_count = 125
│   ├── average_speed = 38.5
│   ├── car_count = 80
│   ├── bus_count = 10
│   ├── truck_count = 15
│   ├── new_energy_count = 20
│   └── carbon_emission = 32.6
│
└── timestamp
    └── 2026-08-20T20:50:01
```

# 十、Tag 和 Field 怎么区分？

这个地方非常重要。

### Tag

用于：

> **经常查询、过滤、分组的数据**

例如：

```text
sensor_id
road_id
direction
vehicle_type
```

例如你经常查询：

```sql
WHERE road_id = 'ROAD-001'
```

那么 `road_id` 很适合作为 Tag。

---

### Field

用于：

> **真正的业务数值**

例如：

```text
vehicle_count
average_speed
carbon_emission
```

因为：

```text
vehicle_count = 125

average_speed = 38.5

carbon_emission = 32.6
```

这些是测量值。

# 十一、写入 InfluxDB

假设使用 InfluxDB Java Client，Repository 可以设计成：

```java
@Repository
@RequiredArgsConstructor
public class InfluxTrafficRepository
        implements TrafficTimeSeriesRepository {

    private final WriteApiBlocking writeApi;

    @Value("${influxdb.bucket}")
    private String bucket;

    @Value("${influxdb.org}")
    private String org;

    @Override
    public void save(
            TrafficFlowDTO trafficFlow,
            CarbonEmission emission) {

        Point point = Point
                .measurement("traffic_flow")
                .addTag("sensor_id",
                        trafficFlow.getSensorId())
                .addTag("road_id",
                        trafficFlow.getRoadId())
                .addField("vehicle_count",
                        trafficFlow.getVehicleCount())
                .addField("average_speed",
                        trafficFlow.getAverageSpeed())
                .addField("car_count",
                        trafficFlow.getCarCount())
                .addField("bus_count",
                        trafficFlow.getBusCount())
                .addField("truck_count",
                        trafficFlow.getTruckCount())
                .addField("new_energy_count",
                        trafficFlow.getNewEnergyCount())
                .addField("carbon_emission",
                        emission.getTotalEmission())
                .time(
                    trafficFlow.getCollectTime()
                        .atZone(ZoneId.systemDefault())
                        .toInstant(),
                    WritePrecision.MS
                );

        writeApi.writePoint(bucket, org, point);
    }
}
```

这样一次交通数据就被写成一个 InfluxDB Point。

# 十二、Spring Boot 配置

例如：

```yaml
influxdb:
  url: http://localhost:8086
  token: ${INFLUXDB_TOKEN}
  org: greentraffic
  bucket: traffic
```

然后创建：

```java
@Configuration
public class InfluxDBConfig {

    @Bean
    public InfluxDBClient influxDBClient(
            InfluxProperties properties) {

        return InfluxDBClientFactory.create(
                properties.getUrl(),
                properties.getToken().toCharArray(),
                properties.getOrg(),
                properties.getBucket()
        );
    }

    @Bean
    public WriteApiBlocking writeApiBlocking(
            InfluxDBClient client) {

        return client.getWriteApiBlocking();
    }
}
```

生产环境不要把 Token 直接写进 Git：

```yaml
token: ${INFLUXDB_TOKEN}
```

然后：

```bash
export INFLUXDB_TOKEN=xxxxxx
```

# 十四、InfluxDB 和 MySQL 应该怎么分工？

我非常建议你的 GreenTraffic **不要所有东西都放 InfluxDB**。

可以采用：

```text
                    GreenTraffic
                         │
            ┌────────────┴────────────┐
            │                         │
            ▼                         ▼
       MySQL/PostgreSQL             InfluxDB
       关系型业务数据                时序数据
            │                         │
            │                         │
       ┌────┼─────┐             ┌─────┼─────┐
       ▼    ▼     ▼             ▼     ▼     ▼
      用户  道路   传感器        车流   速度   碳排放
      配置  信息   配置          数据   数据   数据
```

### MySQL

适合：

```text
用户
角色
权限
道路
路口
传感器配置
车辆基础信息
告警规则
优化规则
系统配置
```

### InfluxDB

适合：

```text
实时车流量
平均速度
车辆数量
拥堵指数
碳排放量
空气质量
传感器采集数据
```

# 十五、为什么不把 TrafficFlow 做成 JPA Entity？

因为两种数据性质不同。

比如：

```text
TrafficFlow
```

如果每 5 秒一个传感器写一条：

```text
100 个传感器
×
12 次/分钟
×
60 分钟
×
24 小时
```

一天：

```text
1,728,000 条
```

如果传感器更多，数据量会非常大。

这正是时序数据库擅长的场景。

所以建议：

```text
model
│
├── entity
│   └── Road.java
│   └── Sensor.java
│   └── Vehicle.java
│
└── dto
    └── TrafficFlowDTO.java
```

这样结构就很清晰。

### 最关键的一点

**不要把“写 InfluxDB”理解成 Simulator 的职责。**

更合理的职责划分是：

> **Simulator = 数据生产者**
> **Core = 数据处理者**
> **InfluxRepository = 数据持久化者**
> **InfluxDB = 时序数据存储**
> **Push = 数据实时消费者**
> **API = 数据查询入口**

这样设计以后，未来你的 `simulator` 可以非常容易替换成：

```text
真实传感器
    ↓
MQTT / Kafka
    ↓
TrafficDataService
    ↓
Core
    ↓
InfluxDB
```

而 Core、InfluxDB、Push、API **基本都不用重构**。这会比“Simulator 直接写 InfluxDB”的架构更适合你这个项目。
