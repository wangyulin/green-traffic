**结论**

就文档当前聚焦的“交通指标读写六边形链路”而言，项目已**基本符合设计方向**：

```text
REST / Scheduler / Spring Event / MQ Consumer
  -> Input Port
  -> Application Service
 -> MetricWritePort / MetricQueryPort (已迁移→ TrafficMetricStore)
  -> InfluxDB / VictoriaMetrics Adapter
```

旧 `TrafficRepository`、`TrafficDataRepository` 双链路已清理，存储切换也统一到 `traffic.storage.type`。但若以文档的核心原则“Core 只定义做什么，Infrastructure 决定怎么做”为严格标准，仍有几处需要继续改进。

**需要优先处理**

1. **RocketMQ 的 Profile 与生产配置不一致，生产消息链路实际不可用。**  
   `application-prod.yml` 使用 `messaging.type: rocketmq`，但 `RocketMQMessagePublisher.java:19` 和 `RocketMQMessageSubscriber.java:22` 都只在 `test` Profile 创建。

   生产中 `EventToMessageBridge.java:24` 会尝试向 RocketMQ 转发，但 `MessageRouter.java:18` 找不到可用 Publisher，运行时会抛异常。应将 RocketMQ 适配器绑定到明确的 `messaging.type=rocketmq` 条件，或至少启用 `prod` Profile。

2. **非 `events` 模式下，Spring 事件和 MQ 消费链路会导致同一指标重复写入。**  
   `CarbonEmissionEventListener.java:29` 对 `TrafficMetric` Spring Event 直接调用写入用例；同时 `EventToMessageBridge.java:24` 会将同一事件投递到消息系统，之后 `TrafficMetricMessageConsumer.java:39` 又会写入一次。

   应明确二选一：
   - `events` 模式：Spring Event Listener 直接调用用例；
   - `rocketmq` 模式：仅 Bridge 发布消息，Consumer 调用用例。

   推荐以 `messaging.type` 条件装配两个不同的输入适配器，避免靠方法内 `if` 分支控制。

3. **VictoriaMetrics 写入和查询的数据模型不匹配。**  
   `VictoriaMetricAdapter.java:173` 写入的是 Influx Line Protocol：`traffic_metric` 是 measurement，`trafficFlow`、`averageSpeed`、`co2Emission` 是 fields。VictoriaMetrics 在接收 Influx 格式后通常按 field 展开为独立 Prometheus metric。

   但查询实现默认查询 `traffic_metric`，并只把返回 sample 映射到 `trafficFlow`，`VictoriaMetricAdapter.java:67`。这会导致 VM 查询可能查不到数据，即使查到也丢失平均速度和碳排放。

   应明确 VM 的指标约定，例如拆为：

   ```text
   traffic_metric_traffic_flow
   traffic_metric_average_speed
   traffic_metric_co2_emission
   ```

   然后通过时间戳和标签聚合为一个 ~~MetricPoint~~（已迁移为域对象 `TrafficMetric`）；或改用 VictoriaMetrics 的 JSON/Prometheus Remote Write 模型，并为该适配器补真实端到端集成测试。

**架构与模块改进**

4. **Core 仍直接依赖 Spring、MyBatis 与 MySQL，违反“核心独立于基础设施”。**  
   `pom.xml` 仍引入了 `spring-boot-starter`、`mybatis-spring-boot-starter` 与 `mysql-connector-j`；应用服务也带有 `@Service`，如 `MetricApplicationService.java:11`。

   建议：
   - 从 Core 移除 MyBatis、MySQL、Spring Boot runtime 依赖；
   - 将 Bean 创建移动到 Infrastructure 的 `@Configuration`；
   - Core 保持普通 Java 类，只依赖模型与端口接口。

   `@Service` 本身不影响当前运行，但会让 Core 与 Spring 生命周期耦合，未来替换 DI 框架或做纯单元测试时成本更高。

5. **领域模型和端口的模块归属不够清晰。**  
   `TrafficMetric` 的包名是 `com.greentraffic.model...`，但源码实际位于 `green-traffic-common`，而不是 `green-traffic-model`。另一方面，`MetricWritePort`、`MetricQueryPort` 位于 Common。

   更清晰的职责建议是：

   ```text
   green-traffic-model
     -> TrafficMetric、EnergyRecord 等领域模型

   green-traffic-core
     -> input ports、output ports、commands、application services

   green-traffic-common
     -> 通用响应、通用消息契约、无业务归属的工具
   ```

   这会让“端口由 Core 定义”的所有权更清楚，也避免 Common 逐渐变成杂项容器。

6. **测试控制器仍位于生产 API 源码。**  
   `TimeSeriesDataTestController.java:15` 与 `VmTestController.java:14` 位于 `src/main`，并直接构造示例命令。

   它们适合迁移到：
   - `src/test` 中的 MockMvc/集成测试；
   - 或一个仅在 `local` / `demo` Profile 启用的 `demo` 包。

   正式 API 应统一使用 Request DTO 和 Response DTO。当前 `MetricsController.java:21` 已是正确方向。

**次要改进**

- `GreenTrafficApplication.java:18` 在启动时强制执行 `SELECT 1`。这让 API 启动与 MySQL 强绑定；数据库不可用时应用无法启动，即使当前仅使用 Influx/VM。可改为 `HealthIndicator`，或将数据库探测放到明确启用的基础设施配置。
- `pom.xml` 的 Spring runtime 依赖通常可以移除；Common 应是无框架依赖的契约模块。
- `pom.xml` 引入 Influx Client，但当前没有对应源码实现。应删除未使用依赖，或将 Push 设计成订阅 `MessageSubscriber` / 独立 Push Port，而不是直接访问存储。
- Infrastructure 测试仍保留 JUnit 3 的 `junit:3.8.1`，同时使用 JUnit 5 的 Spring Boot Test；建议删除旧 JUnit 依赖与旧样板测试。
- 现有测试主要是 MockMvc 和 Mockito 单元测试。应补充 InfluxDB、VictoriaMetrics 与 RocketMQ 的 Testcontainers 集成测试，特别覆盖：
  - Influx 写入后可按标签查询；
 - VM 写入与查询返回完整 ~~MetricPoint~~（已迁移为域对象 `TrafficMetric`）；
  - `events`、`rocketmq` 两种模式不会重复写入；
  - `traffic.storage.type` 下恰好装配一个读端口和一个写端口。

**总体评价**

指标核心路径已经从“两套仓储并存”收敛为文档所建议的端口/适配器结构，方向正确且主要边界已建立。下一阶段不应继续大规模删除代码，而应优先修正 RocketMQ Profile、事件重复写入和 VictoriaMetrics 查询模型这三个实际运行风险；随后再做 Core 去 Spring 化及模型/端口模块归位。
