# 一、先判断：当前项目距离“标准六边形”到底还有多远

现在的核心结构大致已经变成：

```text
                ┌─────────────────────┐
                │     API Adapter     │
                │   Controller        │
                └──────────┬──────────┘
                           │ Input Port
                           ▼
                ┌─────────────────────┐
                │       Core          │
                │                     │
                │ Application Service │
                │ Input Port          │
                │ Output Port         │
                └──────────┬──────────┘
                           │
                  Output Port
                           ▼
                ┌─────────────────────┐
                │ Infrastructure      │
                │ DB / MQ / SUMO ...  │
                └─────────────────────┘
```

这部分方向是对的。

例如 `MetricsController` 已经不是直接调用 Repository，而是依赖：

`WriteTrafficMetricUseCase`

然后：

`MetricApplicationService -> MetricWritePort`

这是标准六边形的核心思路。实际代码里 `MetricsController` 注入的是 `WriteTrafficMetricUseCase`，而 `MetricApplicationService` 注入的是 `MetricWritePort`。([GitHub][2])

所以我不会说“这个项目没有六边形架构”。

**真正的问题是：六边形的骨架已经搭出来了，但是边界内部仍然混入了原来的分层架构/共享模型/技术契约。**

# 二、问题 1：`core` 的应用层直接依赖 `model` 模块里的实体

这是我认为目前最重要的问题之一。

`TrafficMetricQueryApplicationService`：

```java
import com.greentraffic.model.entity.traffic.TrafficMetric;
```

然后：

```java
public List<TrafficMetric> query(Instant start, Instant end) {
    return queryPort.query(start, end, java.util.Map.of()).stream()
        .map(this::toTrafficMetric)
        .toList();
}
```

也就是说：

```text
green-traffic-core
       ↓
green-traffic-model
```

而 `TrafficMetric` 作为查询结果直接穿过了 Core Application Service。([GitHub][3])

### 为什么这不符合“完全标准”的六边形

六边形最关键的不是有没有 `port` 这个目录，而是：

> **业务核心应该拥有自己的业务模型和业务契约，外围模型不能反过来定义核心的接口。**

现在实际上是：

```text
model
  └── TrafficMetric
          ↑
          │
core.application
```

这意味着 `model` 模块实际上在参与定义 Core 的业务 API。

尤其是如果 `green-traffic-model` 里的 `entity/traffic` 最终是数据库 Entity，那么问题更明显：

```text
DB Entity
   ↓
Core Application
   ↓
API
```

这就把持久化模型带进了业务核心。

---

## 正确改法

把核心业务对象移动到 Core 的领域内部：

```text
green-traffic-core
└── domain
    └── traffic
        └── TrafficMetric.java
```

或者：

```text
green-traffic-core
└── model
    └── TrafficMetric.java
```

但这个 `TrafficMetric` 必须是**业务对象，而不是 JPA Entity**。

然后：

```text
core
 ├── domain
 │    └── TrafficMetric
 │
 ├── application
 │    └── TrafficMetricQueryApplicationService
 │
 └── port
      ├── input
      └── output
```

数据库实体放到：

```text
green-traffic-infrastructure
└── persistence
    └── entity
        └── TrafficMetricJpaEntity
```

最终：

```text
TrafficMetric
      ↑
     Core
      ↓
TrafficMetricJpaEntity
      ↓
    MySQL
```

而不是：

```text
TrafficMetricJpaEntity
      ↑
     Core
```

# 三、问题 2：查询 Port 的设计已经暴露出“通用 Repository 思维”

这个问题非常具体。

现在：

```java
return queryPort.query(start, end, java.util.Map.of())
```

这里非常值得注意。

`TrafficMetricQueryApplicationService` 明明只有：

```text
start
end
```

两个业务查询条件，却给 Output Port 传：

```java
Map.of()
```

这说明当前 Port：

```java
query(Instant start, Instant end, Map ...)
```

实际上不是围绕具体业务用例设计的，而是一个**通用查询 Repository 接口**。

这和六边形架构的思想有冲突。

---

## 为什么这是一个真实问题

六边形 Port 应该描述：

> Core 为了完成某一个业务能力，需要外部提供什么能力。

而不是：

> 给我一个万能 Repository，我可以传各种参数。

现在这个：

```java
Map<String, Object>
```

实际上是一个典型的“万能查询参数袋”。

以后很容易变成：

```java
query(start, end, Map.of(
    "roadId", roadId,
    "direction", direction,
    "vehicleType", vehicleType,
    "xxx", xxx
));
```

最后 Port 退化成：

```text
万能 Repository
```

---

## 具体改法

现在：

```java
MetricQueryPort.query(
    Instant start,
    Instant end,
    Map<String, Object> conditions
)
```

改成业务查询对象：

```java
public record TrafficMetricQuery(
    Instant start,
    Instant end,
    RoadId roadId,
    Direction direction,
    VehicleType vehicleType
) {}
```

然后：

```java
public interface TrafficMetricQueryPort {

    List<MetricPoint> query(TrafficMetricQuery query);

}
```

Application：

```java
public List<TrafficMetric> query(TrafficMetricQuery query) {
    return queryPort.query(query)
        .stream()
        .map(this::toTrafficMetric)
        .toList();
}
```

这样 Port 表达的是：

> “我要查询交通指标”

而不是：

> “我要执行一个带 Map 参数的数据库查询”。

# 四、问题 3：`MetricApplicationService` 本身几乎只是一个 DTO 搬运工

实际代码是：

```java
public void write(WriteTrafficMetricCommand command) {
    MetricPoint p = toMetricPoint(command);
    writePort.write(List.of(p));
}
```

批量也是：

```java
List<MetricPoint> points =
    commands.stream()
        .map(this::toMetricPoint)
        .toList();

writePort.write(points);
```

它实际上没有任何业务行为。([GitHub][4])

这不是说“代码少就是错”。

问题在于现在的业务流：

```text
API Request
   ↓
Command
   ↓
ApplicationService
   ↓
MetricPoint
   ↓
OutputPort
```

Core 没有真正承担业务语义。

---

## 具体应该怎么改

如果“写入交通指标”本身确实只是一个采集写入用例，那么可以保留 Application Service。

但不要再人为制造：

```text
Request
Command
MetricPoint
TrafficMetric
```

这么多只是字段搬运的对象。

应该明确区分：

### 外部输入

```java
TrafficMetricWriteCommand
```

### Core 业务对象

```java
TrafficMetric
```

### 输出 Port DTO

只有当外部 Sink 的数据格式确实不同的时候，才需要：

```java
TrafficMetricPoint
```

否则现在：

```text
Command → MetricPoint
```

只是换名字。

# 五、问题 4：`TrafficMetricQueryApplicationService` 反而把 Core 的模型转换成了 `model` 模块模型

这里是一个非常明显的边界反转。

现在：

```java
private TrafficMetric toTrafficMetric(MetricPoint point) {
    return new TrafficMetric(
        point.roadId(),
        point.direction(),
        point.vehicleType(),
        ...
    );
}
```

也就是：

```text
Output Port DTO
      ↓
green-traffic-model.TrafficMetric
```

([GitHub][3])

如果 `TrafficMetric` 是真正的领域模型，这个方向就应该反过来：

```text
Infrastructure
      ↓
Port DTO
      ↓
Core
      ↓
Domain TrafficMetric
```

而不是让 Core 把数据重新组装成外部 `model` 模块的对象。

# 六、问题 5：`common` 和 `core.port` 同时存在消息类型契约

这个问题项目本身已经暴露得非常明确。

当前仓库同时存在：

```text
com.greentraffic.common.messaging.TrafficMessageTypes
```

以及：

```text
com.greentraffic.core.port.output.messaging.TrafficMessageTypes
```

仓库源码说明中也明确指出旧的 common 版本仍然保留，只是 Deprecated。([GitHub][1])

这不是“未来可能重复”。

**现在就已经重复了。**

---

## 为什么这是六边形问题

消息类型实际上属于：

```text
Core ↔ Messaging Adapter
```

之间的业务通信契约。

所以正确位置应该是：

```text
core
└── port
    └── output
        └── messaging
            └── TrafficMessageTypes
```

然后：

```text
RocketMQ Adapter
Spring Event Adapter
Push Adapter
```

全部依赖 Core Port。

而：

```text
common
```

不应该定义业务相关的：

```text
TrafficMessageTypes
```

否则：

```text
common
   ↑
Infrastructure
   ↑
Core
```

这种共享模块会逐渐重新成为“隐形依赖中心”。

---

## 具体改法

直接删除：

```text
green-traffic-common
└── messaging
    └── TrafficMessageTypes
```

然后让所有实现统一引用：

```java
com.greentraffic.core.port.output.messaging.TrafficMessageTypes
```

这个改动不是重新设计，是**把已经存在的重复契约真正收口**。

# 七、问题 6：API 层已经绕过统一响应模型

`MetricsController` 当前：

```java
@PostMapping("/write")
public ResponseEntity<String> write(
        @RequestBody TrafficMetricWriteRequest request) {

    writeUseCase.write(request.toCommand());

    return ResponseEntity.ok("accepted");
}
```

([GitHub][2])

项目自己的 common 模块已经有：

```text
ApiResponse<T>
```

但这里没有使用。

所以当前实际状态是：

```text
Common 定义统一 API Response
          ↓
Controller 没使用
```

这不是架构理论问题，而是现有代码已经出现的契约不一致。

---

## 改法

例如：

```java
@PostMapping("/write")
public ApiResponse<Void> write(
        @Valid @RequestBody TrafficMetricWriteRequest request) {

    writeUseCase.write(request.toCommand());

    return ApiResponse.success();
}
```

更重要的是：

**Controller 只负责 Adapter 工作。**

所以：

```text
HTTP Request
    ↓
Request DTO
    ↓
Command
    ↓
Input Port
```

而不是：

```text
HTTP Request
    ↓
直接构造 Core Domain
```

目前 `request.toCommand()` 这个方向其实是比较正确的，应该继续坚持。

# 十二、Spring Event 目前更像“模块通信机制”，而不是六边形 Port

项目中存在：

```text

ProcessedEvent

```

以及 Infrastructure 中：

```text

```

这本身没有问题。

```text
   ↓

      ↓
```

```text
      ↓
Input Port
```

而不是：

```text

```

# 十五、按优先级，我不会建议你“大重构”，而是按这个顺序改

| 优先级 | 当前实际问题                                                       | 改法                                      |
| --- | ------------------------------------------------------------ | --------------------------------------- |
| P0  | Core Application 直接返回 `model.TrafficMetric`                  | 把领域模型收回 Core                            |
| P0  | `MetricQueryPort` 使用 `Map` 泛化查询                              | 改成明确的 Query 对象                          |
| P0  | common 与 core 同时存在 `TrafficMessageTypes`                     | 删除 common 旧业务契约                         |
| P1  | API Controller 没使用现有 `ApiResponse`                           | 统一 REST Adapter 输出                      |
| P1  | `TrafficMetric` / `MetricPoint` / Request/Command 之间存在大量字段搬运 | 明确 Domain / Port DTO / Adapter DTO 三层职责 |
| P1  | Simulator/Spring Event 与 Core 的入口边界不够清晰                      | 全部经 Input Port                          |
| P1  | Infrastructure Adapter 要确保只实现 Core Output Port               | 禁止 Core 反向依赖 Infrastructure             |
| P2  | 模块名称仍然偏“技术模块”                                                | 暂时不动 Maven，先修依赖方向                       |
| P2  | Core Application Service 业务逻辑非常薄                             | 在边界修正后再判断哪些是真正业务逻辑                      |

# 十六、最关键的一点：这个项目不是“重构成六边形”，而是“把已经做了一半的六边形做完整”

我反而认为这个项目目前**最不应该做的事情**是：

> 把所有代码重新拆成 `domain/application/infrastructure/interfaces` 四层，然后全部搬一遍。

因为现在已经有：

```text
core
 ├── application
 └── port
     ├── input
     └── output
```

这已经是正确的方向。([GitHub][9])

真正应该做的是把现在这些“残留边界”清掉：

```text
                当前

API
 │
 ▼
Input Port
 │
 ▼
Core
 │
 ├──────────────→ model       ← 问题
 │
 ├──────────────→ common      ← 部分问题
 │
 ▼
Output Port
 │
 ▼
Infrastructure
```

变成：

```text
                 最终

API Adapter
    │
    ▼
Input Port
    │
    ▼
┌─────────────────────┐
│        CORE         │
│                     │
│ Domain              │
│ Application         │
│ Input Port          │
│ Output Port         │
└──────────┬──────────┘
           │
           ▼
     Output Adapter
           │
           ▼
   DB / MQ / SUMO / WS
```

## 最终评价

如果让我给当前代码一个六边形架构完成度判断：

**不是 0 分，也不是“伪六边形”。**

更准确地说：

> **核心 Port 设计已经建立，API → Input Port、Application → Output Port 的主干是正确的；目前主要问题集中在“Core 内部仍然被外部 Model/共享契约污染”，以及部分 Port 仍然保留传统 Repository/通用参数的设计。**

其中我认为最应该马上改的三个点就是：

**① `TrafficMetricQueryApplicationService` 不应该直接依赖 `green-traffic-model` 的 `TrafficMetric`；**

**② `MetricQueryPort` 不应该用 `Map` 做万能查询参数；**

**③ `TrafficMessageTypes` 不应该同时存在于 `common` 和 `core.port`。**

这三个都是**当前代码已经存在的架构问题**，不是我假设未来可能发生的问题。([GitHub][3])

另外，当前 `MetricsController → WriteTrafficMetricUseCase → MetricApplicationService → MetricWritePort` 这条链路本身是值得保留的，不建议推倒重做。([GitHub][2])
