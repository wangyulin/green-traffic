# 3. 什么叫 Input Port？

这是后面整个改造的核心。

很多人第一次接触 Hexagonal Architecture，会把：

```java
@RestController
```

理解成 Input Port。

其实不是。

正确理解：

```text
Controller = Input Adapter

Input Port = 业务用例接口
```

例如现在：

```java
@PostMapping("/write")
public ResponseEntity<String> write(@RequestBody TrafficMetric metric) {
    metricService.write(metric);
    return ResponseEntity.ok("accepted");
}
```

这里：

```text
MetricsController
       │
       ▼
MetricService
```

实际上 Controller 直接依赖了：

```java
MetricService
```

如果要做标准六边形架构，我更建议变成：

```text
MetricsController
       │
       ▼
MetricWriteUseCase
       │
       ▼
MetricApplicationService
       │
       ▼
MetricWritePort  (已迁移→ TrafficMetricStore)
       │
       ▼
Influx / VM
```

例如：

```java
public interface MetricWriteUseCase {

    void write(TrafficMetric metric);

}
```

这个：

```java
MetricWriteUseCase
```

就是：

> **Input Port**

Controller 只知道：

```java
MetricWriteUseCase
```

而不知道：

```java
MetricApplicationService
```

---

# 4. 为什么一定要这样？

因为你现在实际上已经出现了一个很明显的问题：

```java
private final MetricService metricService;
```

未来如果你出现：

```text
HTTP调用
MQ调用
定时任务
WebSocket
AI Agent
批处理
测试程序
```

它们都可能需要执行：

```text
写入交通碳排放数据
```

如果没有 Input Port：

```text
HTTP Controller ───────┐
                        │
MQ Consumer ───────────┤
                        ▼
                   MetricService
                        ▲
定时任务 ───────────────┘
```

所有入口都直接认识具体 Service。

而有 Input Port：

```text
HTTP Controller ───────┐
                        │
MQ Consumer ───────────┤
                        ▼
                MetricWriteUseCase
                        │
                        ▼
                MetricApplicationService
                        │
                        ▼
                  Output Ports
```

于是：

> **入口与业务实现彻底解耦。**

这就是 Port Input 真正存在的意义。

# 5. 你现在的 Output Port 也有一个明显问题

你现在：

```java

    boolean save(TrafficMetric data);

    boolean saveBatch(List<TrafficMetric> dataList);

    List<TrafficMetric> findByRoadId(...);

    Double findAverageCo2Emission(...);

    boolean isAvailable();

    void cleanOldData(...);
}
```

这个接口实际上已经开始出现：

> **“万能 Repository”问题。**

因为它同时承担了：

```text

批量写
查询道路数据
计算平均碳排放
健康检查
清理数据
```

这意味着它实际上是：

```text
TrafficDataRepository
        ↓
什么都管
```

这会导致未来 MySQL、InfluxDB、VictoriaMetrics 的能力越来越难统一。

# 6. 更推荐拆成多个 Output Port

```java
public interface MetricWritePort {

       void write(List<MetricPoint> points); // 注：`MetricPoint` 已迁移为域对象 `TrafficMetric`

```

你项目实际上**已经有这个接口了**：

```java
MetricWritePort
```

这说明之前的设计已经意识到了这个问题。

所以现在不是推倒重来。

而是：

目前实际上出现了两套：

```text

 └── port/output
      └── TrafficDataRepository


common
 └── port/metrics
      ├── MetricWritePort
      └── MetricQueryPort
```

这就是目前架构中一个非常重要的**重复设计/边界冲突**。

# 7. 当前最值得改的 7 个问题

我先给你一个总表，后面我们一个一个动手。

| 优先级 | 当前问题                             | 严重程度  |
| --- | -------------------------------- | ----- |
| ①   | Input Port 缺失/不完整                | ★★★★★ |
| ②   | `TrafficDataRepository` 职责过重     | ★★★★★ |

其中第⑦点尤其值得注意。

你的代码里现在有：

```java
if (metricsSink != null && metricsSink.equalsIgnoreCase("vm")) {
```

然后返回一个：

```java
new TrafficDataRepository() {
```

里面：

```java
return Collections.emptyList();
```

以及：

```java

```

这属于非常危险的架构信号。

因为：

```text

   ↓
实际上没有查询
   ↓
返回空集合 / 0
```

系统表面上是“正常运行”的，但业务结果实际上可能是错误的。

对于**交通碳排放实时监测系统**，这种设计比直接启动失败更加危险。

```text

基础设施类型
+

```

混在了 Profile 里面。

例如：

```yaml

```

里面：

```yaml

  type: events
```

而：

```yaml
application-prod.yml
```

里面：

```yaml

  type: rocketmq
```

```yaml

```

又：

```yaml

  type: events
```

这实际上把：

> “环境是什么”

和：

绑定了。

```text

测试 + VM
```

排列组合越来越多。

最后就会变成：

```text

application-dev-rocketmq.yml
application-test-vm.yml
application-test-rocketmq.yml
application-prod-vm.yml
...
```

这就是典型的：

> **Profile Explosion（配置爆炸）**
